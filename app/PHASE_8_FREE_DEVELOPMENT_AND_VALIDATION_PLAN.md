# Phase 8 — 免費開發與安全驗證計畫

日期：2026-11-08
目標分支：`app/phase-1-planning`
Supabase 測試分支：不建立（避免額外按時計費）
正式環境：唯讀；本階段不執行 SQL migration、資料寫入、Edge Function 部署、Secrets 輪替或網站發布。

## 1. 本階段範圍

- 顧客 App 與官網共用資料服務的設計。
- 會員／訪客訂單權限規格。
- 涼糕、蘿蔔糕訂單與物流規則。
- 老闆管理後台權限規格。
- LINE／付款通知安全修正草案。
- 免費的靜態檢查、程式碼審查與測試案例整理。

員工系統、員工登入、PDA、掃碼出貨及員工日結暫緩，不納入本階段。

## 2. 免費驗證方式

1. 所有程式與 SQL 草案只提交至 GitHub 開發分支，不合併至正式分支。
2. 先做靜態檢查：搜尋硬編碼密鑰、service_role／secret key 暴露、未授權的資料讀寫、前端可控價格／運費及錯誤的付款狀態更新。
3. 對 SQL 草案做人工審查：確認每個 GRANT／REVOKE、RLS policy、函式權限、search_path、角色檢查與相容性。
4. 對 Edge Function 草案做程式碼審查：檢查 JWT／內部簽章、時間戳、nonce、冪等、錯誤回應個資洩漏及 Secret 管理。
5. 以不連接正式資料庫的 mock／fixture 撰寫單元測試，驗證輸入驗證、價格計算、物流規則、狀態轉移及權限判斷。
6. 使用 GitHub diff 與文件清單進行變更審查；每一項變更記錄風險、依賴、驗收條件與回復方式。

## 3. 不可假裝已完成的驗證

免費靜態檢查與 mock 測試不能證明正式 Supabase 的 RLS、資料庫權限、Edge Function Secrets、LINE webhook、付款 webhook 或真實訂單流程已通過整合測試。

因此，在沒有隔離測試資料庫前：
- 不宣稱 P0 個資 RPC 已修復。
- 不宣稱 Edge Functions 已安全部署。
- 不執行任何可能影響正式訂單的權限收斂。
- 不以正式顧客資料進行測試。
- 不把正式專案當作測試環境。

## 4. 正式環境變更門檻

日後若要修改正式環境，必須先向使用者提供具體變更清單，至少包含：
- SQL／Function／網站檔案的精確名稱與差異。
- 受影響的表、RPC、Edge Functions、官網頁面與訂單流程。
- 風險、相容性、備份項目、回復步驟。
- 測試結果及尚未能驗證的項目。

取得使用者對該份具體清單的明確核准後，才可安排正式環境操作。一般性的「好」或同意繼續開發，不代表核准正式部署。

## 5. 完成定義

- [ ] 顧客 App／官網功能需求及共用資料契約完成。
- [ ] 涼糕與蘿蔔糕物流、運費來源及付款狀態規格完成。
- [ ] 會員與訪客訂單讀取權限規格完成。
- [ ] 老闆後台角色權限矩陣完成。
- [ ] P0 LINE 個資 RPC 與通知 Function 修正草案完成。
- [ ] SQL 與 Function 靜態檢查及 mock 測試完成。
- [ ] 官網相容性檢查清單完成。
- [ ] 正式環境變更清單與回復計畫待核准。

## 6. 費用與安全界線

本階段不建立 Supabase paid development branch，不觸發該分支的按時計費。GitHub 開發工作仍受使用者現有 GitHub 方案及服務使用限制影響；不假設任何外部服務必然免費。正式 Supabase 專案維持不變。

# 老爹．涼糕完整 App 與營運平台 — 系統架構規劃

> 狀態：正式規劃文件；尚未代表正式 App 已完成、已連接正式資料庫或已上架。
> Git 分支：`app/phase-1-planning`
> 品牌：老爹．涼糕
> 視覺：曜石黑、香檳金、暖白；繁體中文優先。
> 目標裝置：iPhone、Android、員工 PDA、電腦管理後台。
> 官網：既有網站持續營運；完成驗收前不切換流量、不破壞既有流程。

## 1. 產品定義

採用「一套中央資料、四個使用介面」：

1. 顧客 App（iOS / Android）：商品、購物、免註冊結帳、會員、訂單、優惠、擺攤資訊。
2. 員工 PDA：掃碼、訂單揀貨/包裝/出貨、庫存、現場銷售、會員辨識、餐車/擺攤作業。
3. 老闆管理後台（電腦優先、手機可檢視）：商品、口味、訂單、付款核對、物流、庫存、擺攤、餐車、會員、優惠、員工、報表。
4. 官方網站：保留既有公開網站和購物流程，逐步接入共用會員、商品、訂單與出攤資訊服務。

「串接」指共用正式資料與 API，不代表所有平台必須使用相同畫面或同一套前端程式。

## 2. 顧客 App 功能地圖

### 首頁與品牌內容
- 品牌首頁、活動 Banner、最新公告。
- 商品分類：涼糕、純米涼糕、蘿蔔糕及後續新增品類。
- 今日/近期擺攤資訊入口、收藏地區/市場入口。
- 搜尋、商品推薦、客服/聯絡方式。

### 商品與購物
- 商品列表、詳情、口味/規格、價格、可售狀態。
- 購物車、數量調整、優惠套用、結帳。
- 訂單來源標記：官網、App、員工現場、餐車/擺攤。
- 配送選項依商品與營運規則顯示；冷凍宅配、超商寄放/取貨等需依既有實際服務規則設定，不可把「冷藏寄放」誤寫成「冷藏宅配」。
- 訂單確認、付款指示、配送狀態、訂單查詢。

### 訪客與會員
- 訪客可瀏覽及免註冊下單。
- 免費會員可註冊；官網與 App 共用一個會員帳號。
- 會員中心、個人資料、會員 QR Code、消費紀錄、歷史訂單、優惠券、活動資格。
- 會員市場優惠：由老闆設定適用地點、日期、商品、優惠條件與有效期；現場由 PDA 驗證會員與優惠。
- 舊訂單不得只按姓名或電話自動認領；需經 OTP/Email 驗證、訂單資料核對或客服流程確認本人。

### 擺攤與餐車資訊
- 依縣市/行政區篩選今日及未來出攤行程。
- 每筆行程包含日期、縣市、行政區、場地/市場名稱、完整地址、開始/結束時間、販售口味、公開價格、公告、狀態。
- 地圖位置與導航連結；只有地址/座標經確認後才顯示導航。
- 收藏市場/地區、行程提醒、口味預告、臨時取消/延後/售完通知。
- 顯示售完/剩餘庫存須由現場人員更新或可靠庫存資料支援；不可把未同步庫存當即時保證。

### 通知與活動
- 訂單狀態推播、出攤提醒、活動公告、優惠券到期提醒。
- 推播需取得使用者授權；可在設定中管理通知偏好。
- 刮刮樂/抽獎活動需有活動規則、資格、次數、有效期、兌換紀錄與防重複機制。

## 3. 員工 PDA 功能地圖

### 登入與工作台
- 員工帳號登入、角色/門市/工作站授權。
- 今日待辦、工作站、同步狀態、掃碼入口。
- 網路中斷時只允許明確設計為可離線的工作；恢復連線後需去重同步並保留操作人/時間。

### 訂單作業
- 線上訂單自動進入待處理清單。
- 現場臨時單可建立獨立訂單，標記銷售渠道、收款方式與經手員工。
- 超商寄放訂單與宅配訂單保留各自來源、狀態和欄位語意，透過統一工作清單呈現，不直接合併或覆蓋原始資料。
- 訂單條碼/QR Code 查詢、揀貨、複核、包裝、出貨交接。
- 掃描異常、缺貨、數量不符、重複掃碼均需明確提示及留紀錄。

### 庫存與現場銷售
- 入庫、出庫、調撥、盤點、報損/調整，均記錄原因、操作人、時間與來源。
- 商品條碼與 SKU 對應；尚無條碼的品項可使用內部代碼。
- 擺攤/餐車可建立現場銷售單、退貨/作廢流程與日結。
- 會員 QR Code 掃描後只回傳必要會員狀態與優惠，不在 PDA 暴露不必要個資。
- 價格、折扣及退款規則由伺服器端重新驗證，PDA 不可自行決定最終價格。

## 4. 老闆管理後台

- 營運儀表板：今日訂單、待付款、待出貨、銷售、庫存警示、出攤概況。
- 訂單中心：分來源檢視、搜尋、付款狀態、處理狀態、匯款核對、取消/退款紀錄。
- 商品中心：品類、商品、口味、規格、圖片、價格、可售狀態。
- 庫存中心：倉庫/工作站/餐車/攤位庫存、異動流水、盤點。
- 物流中心：配送方式、運費規則、寄放資訊、託運單號、出貨批次。
- 擺攤中心：行程日曆、地區、地點、時間、口味、價格公開設定、公告、取消/異動。
- 餐車中心：車輛/人員、出攤排程、當日菜單、現場訂單與日結。
- 會員中心：會員資料、驗證狀態、消費紀錄、優惠資格、停權/客服註記。
- 行銷中心：優惠券、會員價、限定活動、刮刮樂規則與兌換紀錄。
- 員工中心：帳號、角色、可管理區域、工作站、權限與操作紀錄。
- 報表中心：依日期/渠道/地區/商品/口味/員工分析銷售與營運。

## 5. 角色與權限

- 顧客：只能存取自己的會員資料、本人訂單與已驗證認領的歷史訂單。
- 一般員工：只看被授權的工作站、訂單與必要資料。
- 倉庫/出貨員：庫存及出貨操作，不得修改會員權限或付款結果。
- 擺攤/餐車員工：只管理被指派的場次、現場銷售及必要會員優惠驗證。
- 主管：可管理授權範圍內人員與作業。
- 老闆/管理員：管理全域設定；高風險操作需記錄審計軌跡。
- 權限必須由伺服器/資料庫政策驗證，不能只靠前端隱藏按鈕。

## 6. 共用資料與整合原則

既有網站程式碼已發現以下資料表（仍須連線檢查實際 schema、欄位、索引、外鍵、RLS 與觸發器）：

- `flavors`
- `cooling_pickup_orders`
- `cooling_pickup_order_items`
- `orders`
- `order_items`
- `order_customers`
- `order_private`
- `food_truck_schedules`

網站程式碼亦曾出現周邊商品/訂單資料表名稱，需在 schema 盤點時再確認是否存在及用途。

整合策略：
1. 先盤點現有資料結構與正式流程，再決定哪些資料表原樣沿用、哪些新增關聯表。
2. 不在未確認 schema 前直接重建、改名、刪除或合併正式資料表。
3. 將不同訂單類型以統一 API/工作視圖呈現，底層保留原始來源與狀態。
4. 商品、口味、價格、可售狀態以單一管理來源發布到官網與 App。
5. 擺攤資訊以共用排程資料提供官網與 App；現有 `food_truck_schedules` 需先檢查欄位能否支援市場、地點、時間、菜單及發布狀態。
6. 會員身份使用 Supabase Auth；會員 profile 以 Auth UID 關聯。現有 `order_customers` 是訂單聯絡資料，不等於會員帳號。
7. 優惠/會員價與現場銷售應由後端計算與驗證，並保存使用紀錄。

## 7. 建議技術分層

- 顧客 App：跨平台 iOS/Android 前端（技術選型待 repo 現況與維護能力評估）。
- PDA：優先採可在目標 PDA 瀏覽器/Android 裝置穩定運作的工作介面；需先確認 PDA 型號、掃描器輸入方式及網路環境。
- 管理後台：響應式 Web 管理介面。
- 官網：維持現有網站，逐步整合共用身份與 API。
- 後端：沿用現有 Supabase 專案前，先做 schema、RLS、Auth、Storage、付款 webhook 與備份盤點。
- API：重要業務規則放在受控後端/資料庫，不在客戶端信任價格、角色、付款狀態或優惠結果。
- 通知：推播服務與既有 LINE 通知方式需先盤點，避免重複發送或漏發。

## 8. 資安與個資原則

- 公開前端只使用 publishable key；service-role/secret key 不得放在 App、PDA 或瀏覽器。
- 所有 exposed schema 資料表啟用 RLS，依角色與資料擁有權建立政策。
- `TO authenticated` 不代表已完成授權；每個讀寫政策都必須限制 owner、工作站或角色範圍。
- 不使用可由使用者自行修改的 user metadata 作為管理權限依據。
- 付款成功只能由可信任的付款回呼/後端查證更新。
- 會員個資最小化；PDA 只顯示完成工作所需資料。
- 敏感操作保留審計紀錄；正式上線前完成備份與復原演練。

## 9. 分階段交付與驗收

### Phase 0 — 現況盤點與安全基線
- 確認 repo 架構、網站部署方式、Supabase schema、RLS、Auth、Storage、付款與通知流程。
- 確認 PDA 型號/掃碼器、員工工作流程、配送規則及實體攤位日結方式。
- 產出資料字典、系統流程圖、風險清單。
- 驗收：不改動正式資料；每個既有流程有文件與測試案例。

### Phase 1 — 共用會員與顧客核心
- 建立免費會員註冊/登入/忘記密碼；訪客免註冊購物。
- 建立會員 profile、會員中心、跨官網/App session 流程。
- 商品讀取、購物車、訂單建立、訂單查詢。
- 歷史訂單認領流程。
- 驗收：訪客與會員都能依規則下單；不同會員無法讀取彼此訂單。

### Phase 2 — 擺攤/餐車資訊與行銷
- 行程管理、縣市篩選、地圖/導航、口味與價格公開設定。
- 收藏地點、提醒、異動公告。
- 會員 QR Code、優惠券、會員價、刮刮樂活動與兌換紀錄。
- 驗收：後台發布後官網/App 一致；優惠重複使用會被拒絕。

### Phase 3 — 員工 PDA、庫存與出貨
- 員工登入與角色授權。
- 訂單接收、掃碼、揀貨、複核、出貨。
- 現場臨時單、擺攤/餐車銷售、會員驗證。
- 庫存流水、盤點、日結。
- 驗收：重複掃碼不重複扣庫存；不同員工不能越權。

### Phase 4 — 老闆後台與報表
- 全域訂單/商品/庫存/會員/優惠/員工/排程管理。
- 付款核對、物流管理、報表。
- 驗收：操作紀錄可追查；高風險操作需確認與權限。

### Phase 5 — 全面測試與商店上架
- iOS、Android、PDA、桌面瀏覽器相容性。
- 購物/付款/退款/缺貨/取消/斷網/重複請求/權限測試。
- 隱私政策、服務條款、商店素材、Apple/Google 開發者帳號與審核。
- 灰度/分批上線；保留官網原流程與回復方案。

## 10. 開始寫正式程式前仍需取得的資料

- Supabase 實際 schema、RLS policies、Storage policies、Auth 設定。
- 官網目前付款、運費、訂單狀態、超商寄放及宅配完整規則。
- PDA 品牌/型號、作業系統、掃碼器模式與員工流程。
- 各角色名單與權限矩陣。
- 會員註冊方式的最終確認（目前建議 Email + 密碼起步）。
- 會員優惠計算規則、適用場次/商品、能否與其他優惠併用。
- 推播/LINE 通知目前使用方式與供應商。
- App 上架所需的品牌素材、隱私政策及客服聯絡資料。

## 11. 本階段明確不做的事

- 不停用或覆蓋正式官網。
- 不直接刪除/合併現有訂單表。
- 不將訂單聯絡資料直接視為會員帳號。
- 不在尚未盤點 RLS 前公開會員/訂單 API。
- 不把 service-role key 放入任何前端。
- 不宣稱 App 已可下載或已上架。

# 老爹．涼糕 App — 執行階段工作計畫

> 更新日期：2026-11-08
> 分支：`app/phase-1-planning`
> 本文件是開發執行計畫，不代表 App 已上線或正式資料庫已變更。

## 1. 本次已確認的執行範圍

優先進行：
- 顧客 App：iOS / Android。
- 老闆管理後台：桌面優先、手機可檢視。
- 既有官網持續營運，逐步共用會員、商品、訂單及排程資料。

暫緩：
- 員工 PDA、掃碼器整合及員工現場工作站。待使用者採購 PDA 後，再依實際品牌、型號、Android 版本及掃碼器輸入模式規劃。
- 不因 PDA 暫緩而阻擋顧客 App 和老闆後台的規劃工作。

## 2. 現況資料盤點摘要（唯讀）

Supabase 專案：既有正式專案（本次只讀檢查，未執行任何 DDL/DML）。

已確認存在的核心資料：
- 商品/口味：`flavors`（目前 36 筆）。
- 宅配訂單：`orders`、`order_items`、`order_private`。
- 超商寄放訂單：`cooling_pickup_orders`、`cooling_pickup_order_items`。
- 訂單聯絡資料：`order_customers`（這不是會員帳號）。
- 餐車/擺攤排程：`food_truck_schedules`、`food_truck_schedule_flavors`。
- 每日訂購設定：`daily_order_settings`、`daily_order_regions`、`daily_order_flavors`。
- 付款/取貨設定：`payment_settings`、`pickup_settings`。
- PDA/現場銷售相關資料表存在，但本階段不實作員工端。

重要資料語意：
- 宅配與超商寄放是不同流程，保留各自的訂單主表、狀態及欄位。
- `orders.customer_user_id` 已存在，可作為未來已登入會員訂單關聯的一個依據；仍須檢查舊資料來源、RLS 與建立訂單 RPC，不能只靠姓名/電話自動認領歷史訂單。
- `food_truck_schedules` 已包含日期、類型、標題、地區、時間及啟用狀態；仍須確認地址/座標、臨時異動、公開菜單和提醒功能是否需要擴充。
- 商品/價格以既有正式資料為準，不在 App 端硬編碼或自行推算運費。

## 3. 必須先處理的安全阻擋項目

本次 Supabase 表清單檢查發現：
- `public.merch_backend_sync` 的 RLS 目前為停用狀態。Supabase Advisor 將其標示為 critical，指出該表可能對 anon/authenticated 角色暴露。
- 不能直接只開啟 RLS 就算修復，因為沒有合適 policy 可能令既有同步流程停止；必須先確認該表用途、誰需要讀寫、前端/後端使用方式，再制定最小權限 policy。
- 先前安全盤點亦發現部分 `merch_*` 管理 policy 使用 `true`，以及多個 SECURITY DEFINER RPC 可由公開或登入角色呼叫的警示。警示不等於已證實可利用漏洞，但必須逐一檢查函式內部授權及資料暴露。
- Auth 的 leaked password protection 目前為停用狀態，列入上線前安全設定檢查。

**本文件建立期間不會修補上述正式資料庫項目。** 修補前需提出具體 SQL、功能影響、回復方式及測試計畫，取得使用者對該項變更的明確授權後才可執行。

## 4. 開發順序

### A. 顧客 App MVP
1. 黑金品牌首頁、公告、商品分類與商品詳情。
2. 訪客購物車及免註冊結帳流程。
3. 免費會員註冊、登入、登出、忘記密碼。
4. 會員中心、個人資料、會員 QR Code（先定義資料契約，未經授權不開放現場核銷）。
5. 訂單查詢：宅配與超商寄放分開呈現。
6. 餐車/市場行程：縣市/區域篩選、日期、地點、時間、口味、價格、公告。
7. 訂單與出攤通知：需使用者授權通知，並提供偏好設定。

### B. 老闆管理後台 MVP
1. 安全管理員登入及伺服器端角色授權。
2. 營運總覽：訂單量、待付款、待處理、出貨狀態。
3. 商品/口味：名稱、分類、圖片、價格、啟用狀態。
4. 訂單中心：不同訂單來源分區管理，不合併原始表。
5. 餐車/擺攤排程：日期、類型、地區、地點、時間、當日口味及公開狀態。
6. 會員與優惠設定：先建立規則管理規格；折扣與適用條件由老闆設定，不預設固定折扣。
7. 高風險操作需二次確認及審計紀錄。

### C. 官網共用資料整合
1. 官網持續使用既有流程，先定義共用 API 與資料契約。
2. 新會員使用 Supabase Auth；會員 profile 以 Auth UID 關聯。
3. 訪客仍可免註冊購物。
4. 既有訂單保留原始來源與狀態；歷史訂單需經本人驗證後才可認領。
5. App/官網的商品、價格、排程資料來自共同來源，避免兩邊各自硬編碼。
6. 完成回歸測試後才逐步開放，不直接切換正式流量。

### D. PDA（暫緩）
設備採購完成後再決定掃碼器整合方式、離線能力、工作站權限及硬體相容性。

## 5. 上線前必要驗收

- 訪客可下單，會員可登入下單。
- 不同會員無法讀取彼此會員資料或訂單。
- 訂單建立、付款狀態及退款均由可信任後端流程驗證。
- 宅配與超商寄放訂單狀態及配送欄位不互相污染。
- 官網和 App 顯示相同的已發布商品、價格及行程。
- 未發布/停用商品不會被顧客購買。
- 管理員與一般使用者的 API/RLS 權限測試通過。
- 斷網、重複請求、重複付款回呼及錯誤狀態均有測試。
- 完成備份與回復演練、隱私政策及商店上架素材。

## 6. Supabase 變更紀律

- 本階段先使用唯讀方式完成 schema、RLS、RPC、Storage、Auth 及前端呼叫盤點。
- 不在正式資料庫直接建立會員表、修改 policy、改函式或執行 migration，除非使用者對明確變更授權。
- 新表若日後要透過 Data API 存取，需同時確認 Data API exposure/grants 與 RLS；Supabase 自 2026-10-30 起對新建 public schema tables 不再預設自動暴露於 Data API。
- 不把 service_role/secret key 放進 App、官網瀏覽器或任何公開前端。
- 權限判斷不使用使用者可自行修改的 user_metadata。
- 所有 SECURITY DEFINER 函式都必須檢查函式內部授權、固定 search_path 並採最小 EXECUTE 權限。

## 7. 下一個實作交付

先建立不連正式會員/付款資料的顧客 App UI 原型及老闆後台 UI 原型，並以假資料展示主要流程。確認畫面與工作流程後，再逐項實作 Auth、API、RLS 和資料串接。此方式可先驗收介面，同時避免在安全盤點未完成前暴露真實顧客資料。

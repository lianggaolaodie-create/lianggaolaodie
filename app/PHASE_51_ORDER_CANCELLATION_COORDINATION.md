# Phase 51 — 訂單取消、退款與庫存回補協調模型

## 交付
- `app/mock-api/cancellation-model.js`：合成訂單與預留庫存、取消冪等、出貨限制、付款前取消、付款後等待退款、退款成功後一次性回補庫存。
- `app/mock-api/cancellation-model.test.js`：涵蓋未付款取消、冪等重送、key 衝突、已付款待退款、退款確認、重複回補、部分／全部出貨阻擋、處理中人工覆核與錯誤輸入。

## 核心規則
1. 未付款且未進入處理／出貨的訂單可取消；立即釋放預留庫存一次。
2. 已付款訂單提出取消時只進入 refund_pending；不得先標示已退款，也不得先回補庫存。
3. 只有與該取消單綁定的退款 reference 確認成功後，才完成取消、標記 refunded 並回補庫存。
4. 退款未成功或仍處理中，訂單與庫存保持保留狀態，等待重試／人工處理。
5. 已部分出貨或已出貨訂單不允許走整單取消；處理中的訂單要求人工覆核。
6. 相同冪等 key／相同請求回放原結果；相同 key 不同內容拒絕。
7. 取消成功後再次收到相同退款確認，不得重複回補庫存。

## 正式後端必要條件
- 訂單、取消紀錄、退款紀錄、庫存異動必須在資料庫交易內一致提交；鎖定訂單及 SKU 庫存列，避免併發超賣或重複回補。
- 使用唯一索引保證 cancellation idempotency key、refund provider reference 及 stock movement reference 唯一。
- 退款成功事件須先驗證 provider webhook／API 回應與退款金額、幣別、訂單及付款 reference；不可由 App／前端呼叫成功旗標。
- 部分出貨、拆單、多品項取消、折扣分攤、運費退還、發票／稅務、優惠券回復及冷凍／冷藏物流攔截，須按正式業務規則另訂。
- 本模型採整單取消，不代表支援已出貨訂單的部分退款或部分取消。

## 限制
- 純 Node in-memory reference model 與合成測試；不連正式訂單、付款、退款、庫存或 Supabase。
- 不呼叫金流、不發通知、不執行真實庫存異動。
- 正式環境未修改；本階段仍非可上架 App 或正式後端。

# 老爹．涼糕官方 App — 第一階段規劃

> 專案狀態：規劃與資料盤點中（尚未上線、尚未修改正式網站或資料庫）
> 品牌方向：黑金高級質感
> 平台目標：iOS + Android
> 會員登入決策：優先沿用官網既有會員帳號與密碼

## 1. 產品目標

建立一套共用既有官網營運資料的品牌 App，分為三個權限入口：

- 顧客端：瀏覽商品、會員、購物車、下單、付款狀態與訂單查詢。
- 員工端：依權限接收訂單、條碼掃描、出貨核對、庫存與餐車作業。
- 老闆端：訂單總覽、收款狀態、商品/口味、庫存、餐車與營運報表。

官網先維持正常運作。App 不建立第二套商品/訂單主資料；資料整合完成並驗收前，不切換正式流量。

## 3. 會員系統：從零建立（已依使用者確認修正）

使用者已確認：目前官網沒有會員登入功能。因此不再採用「沿用既有會員帳密」的假設，改為建立全新的老爹會員系統，並讓官網與 App 共用同一套身份服務。

建議方案：
1. 使用 Supabase Auth 建立顧客帳號、登入、登出與密碼重設。
2. 第一版以 Email + 密碼註冊登入；完成後可再評估手機簡訊驗證，避免初期增加簡訊費用與 OTP 營運成本。
3. 建立會員個人資料表，透過 Auth UID 與登入身份關聯；密碼只由 Auth 安全管理，不自行存入會員資料表。
4. 官網和 App 共用同一 Supabase Auth 專案、會員資料及 session 規則；註冊一次即可跨平台登入。
5. 既有歷史訂單先完整保留。不得只用姓名或電話自動把舊訂單綁定新會員；應設計電話/Email 驗證、訂單編號核對或人工客服認領流程，確認本人後才關聯歷史訂單。
6. 顧客只能讀取自己的會員資料與已驗證關聯的訂單；RLS 必須以 Auth UID / 已驗證關聯限制資料存取。

第一階段需要先確認的產品決策：新會員註冊方式（Email + 密碼，或手機號碼 + 簡訊驗證）。技術上先以 Email + 密碼作為低成本 MVP 建議方案，等待使用者確認後再實作。

## 5. 視覺規範

- 主背景：曜石黑 / 深炭黑。
- 主要強調色：香檳金；正文使用高對比暖白。
- 卡片：深灰黑、細金線、圓角；避免過多金色大面積填滿。
- 商品照片：沿用官網核准的真實商品圖，不用示意圖冒充正式商品。
- 繁體中文優先，手機小螢幕可讀性優先。
- 顧客端、員工端、老闆端共用品牌識別，但依角色顯示不同導覽與權限。

## 6. 資料與安全原則

- 正式資料仍以既有 Supabase 專案為準；上線前需盤點 schema、foreign keys、RLS policies、Data API grants、Auth provider 與 Storage policies。
- App 前端只使用 publishable key；任何 service-role / secret key 不得放入 App。
- 顧客只能讀取自己的會員資料與訂單；員工依角色授權；管理權限由伺服器端/資料庫政策驗證。
- 不可只靠前端隱藏按鈕作為權限控管。
- 付款成功狀態必須以可信任的付款回呼/伺服器端驗證為準，不可由 App 自行標記已付款。
- 不在 App 本機保存明文密碼或不必要的敏感個資。
- 上線前完成測試帳號、權限測試、資料備份與回復計畫。

# 老爹．涼糕 App 配送與結帳規格

版本：1.0  
狀態：依使用者確認的官網訂購畫面整理；正式串接前仍須核對現行官網欄位與後端流程。

## 1. 訂購入口與服務分類

顧客訂購首頁保留三個清楚分開的入口，不得把不同商品或配送流程混為一談：

1. **送到府（老爹涼糕預約配送）**：老爹自有配送服務，並非一般宅配物流。
2. **超商冷藏寄放（老爹涼糕）**：選擇 7-ELEVEN／全家寄放門市，屬冷藏寄放，不是冷藏宅配。
3. **蘿蔔糕宅配訂購**：獨立商品訂購與宅配流程，獨立管理。

## 2. 送到府－老爹涼糕

依使用者提供的官網畫面，送到府訂購流程及規則如下：

- 顧客選擇配送日期。
- 顧客選擇服務地區。
- 顧客選擇涼糕口味與各口味數量。
- 最低訂購量為 **2 盒**。
- **可混搭不同口味**；結帳時計算所有口味盒數總和，總盒數至少 2 盒。
- 付款方式為 **貨到付款**。
- 此服務由老爹安排送到府，不可標示為一般宅配或交由宅配物流配送。

### 顧客介面
- 先選「送到府」，才顯示日期、地區、口味及數量欄位。
- 即時顯示各口味數量、總盒數及訂單摘要。
- 總盒數未達 2 盒時，不允許送出訂單，並清楚提示最低訂購 2 盒。
- 顯示貨到付款方式。
- 送出後提供訂單編號及訂單狀態查詢。

### 後台管理
- 依送到府訂單獨立建立工作清單。
- 管理可配送日期、服務地區、當日可選口味及可訂購數量；只有管理者已設定開放的日期／地區／口味才可供顧客選擇。
- 後台可檢視訂單日期、地區、口味明細、總盒數、收件聯絡資料、配送備註及貨到付款狀態。
- 可更新接單、備貨、配送中、已送達、取消等適用狀態；實際狀態轉換須配合既有訂單程式確認。
- 貨到付款不得在顧客送單時誤標為已收款；應由有權限的人員在實際收款後核銷。
- 不得自行假設或硬編碼配送費、最低配送金額、配送半徑或時段；若目前官網／後台沒有明確設定，列為待確認項目。

## 3. 超商冷藏寄放－老爹涼糕

- 顧客選擇 7-ELEVEN 或全家及指定寄放門市。
- 最低訂購量為 **2 盒**，可混搭不同口味。
- 依現行官網畫面為 **需先付款**。
- 此服務名稱及說明應使用「超商冷藏寄放」，不得稱為冷藏宅配。
- 門市資料、寄放費、付款狀態、寄放／取件狀態需獨立保存與管理。
- 過去曾有取件期限與寄放費規則，但是否仍有效須由管理者核對；在核對前不可將舊規則寫死為現行規則。

## 4. 蘿蔔糕宅配訂購

- 保留獨立的蘿蔔糕商品、收件資料、宅配方式、運費、付款與訂單狀態。
- 不得套用涼糕送到府的日期／地區選擇、最低 2 盒、混搭口味或貨到付款規則。
- 運費必須讀取已核實的後台設定或正式計價來源，不可使用前端硬編碼數字。
- 蘿蔔糕訂單維持獨立管理及既有官網流程。

## 5. 訂單資料與流程隔離

- 訂單需明確記錄訂購類型／配送類型，讓後台可依類型分流。
- 建立訂單時保存當時的商品、口味、數量、日期、地區、收件／門市資訊、費用及付款方式快照；日後管理者修改設定，不得回頭改變既有訂單內容。
- 訪客與會員均可使用已開放的訂購流程；會員身份與訂單聯絡資料不可混為一談。
- 三種流程的付款與狀態分開管理，不可因共用 App 介面而混用規則。
- 既有資料表及流程（包含 `orders`、`order_private`、`cooling_pickup_orders`、相關 order items、`radish_orders` 等）先保留。完成實際程式碼、RLS、RPC、付款回呼及資料關聯盤點後，才決定是否建立共用 API 或統一訂單檢視；不可直接合併資料表或覆蓋舊流程。

## 6. 官網、App、老闆後台與 PDA

- 官網與顧客 App 共用經核實的商品、日期、地區、口味、訂單及設定資料。
- 顧客 App、老闆後台及員工 PDA 依角色顯示不同介面與權限。
- 官網現有訂購功能須持續運作；App 上線不得破壞或擅自替換官網流程。
- PDA 的出貨核對／配送操作待設備與現場作業流程確認後再實作；本規格不代表已啟用 PDA 配送功能。

## 7. 上線前待核對事項

1. 送到府目前實際服務縣市／區域、可選日期、配送時段及地址欄位。
2. 送到府是否有配送費、免運條件或其他限制；只依正式設定顯示。
3. 貨到付款的收款核銷方式及訂單狀態流程。
4. 超商冷藏寄放目前有效的寄放費、取件期限、付款及門市資料欄位。
5. 蘿蔔糕宅配運費設定來源、物流方式及付款方式。
6. 三類訂單目前實際寫入的資料表、建立訂單 RPC、RLS 與付款回呼。

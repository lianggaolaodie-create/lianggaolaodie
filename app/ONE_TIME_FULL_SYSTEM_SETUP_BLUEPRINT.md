# 老爹．涼糕 App 全系統一次整合設定總藍圖

日期：2026-11-08  
分支：`app/phase-1-planning`  
目的：依使用者要求，將 App、官網、會員、訂單、配送、付款、庫存、餐車、擺攤與老闆後台視為同一個完整專案規劃；員工系統與 PDA 暫緩，避免零散逐項設定。  
狀態：整合規格與唯讀盤點；尚未套用正式資料庫變更、未開啟訂購、未切換正式官網。

## A. 一次整合原則

1. 一套共用資料與服務層，先完成兩種主要介面：顧客 App／官網、老闆後台。
2. 官網持續運作；App 上線不取代官網，也不直接覆蓋既有頁面。
3. 訪客可購物；會員登入後可查本人訂單、收藏、優惠與會員權益。
4. 所有商品價格、庫存、運費、優惠、配送方式與開放日期由後台／資料庫設定；前端只呈現，不是價格或權限的權威來源。
5. 涼糕與蘿蔔糕訂單資料可在同一管理介面總覽，但保留不同商品、付款、物流、狀態及報表語意。
6. 既有資料表優先延用；新增欄位／表格前先做相容性盤點及備份。
7. 員工帳號、員工管理介面、PDA 掃碼及出貨作業全部暫緩，不納入目前階段驗收。
8. 不把未知物流費、銀行資料、門市 API 或付款串接狀態猜成已設定。

## B. 顧客端（App＋官網）

### 首頁
- 品牌介紹、公告、活動、最新優惠。
- 餐車／擺攤行程、縣市篩選、日期、地點、服務時間。
- 當日販售口味、價格、可用庫存（只有資料可靠同步時才顯示即時庫存）。
- 導航、收藏、提醒、行程異動通知。

### 商品與購物
- 涼糕商品／口味、蘿蔔糕商品獨立分類。
- 商品圖、規格、價格、上架狀態、可訂購狀態。
- 購物車、訪客結帳、會員結帳、訂單編號。
- 商品價格與庫存由資料庫重新核對，不能信任瀏覽器傳入價格。

### 會員
- Supabase Auth 管理登入憑證；會員 profile 以 Auth UID 關聯。
- 訪客購物不強迫註冊。
- 會員中心：個人資料、本人訂單、收藏、優惠券／會員權益、通知設定。
- 舊訂單不得只憑姓名或電話自動認領；需安全驗證或由客服／管理流程協助。
- 會員只能查本人資料與訂單，不能透過訂單編號猜測他人資料。

## C. 物流與取貨（不可混流程）

| 流程 | 適用 | 必要資料 | 付款／狀態 |
|---|---|---|---|
| 涼糕送到府 | 涼糕 | 完整收件地址、配送日期、開放地區 | 既有貨到付款規則；由可信後端確認 |
| 涼糕超商冷藏寄放 | 涼糕 | 超商類型、門市、取件資訊、寄放費、取貨期限 | 既有先付款流程；冷藏寄放不是冷藏宅配 |
| 蘿蔔糕冷凍店到店 | 蘿蔔糕 | 冷凍門市／取件資料 | 依實際簽約與後台開放方式 |
| 蘿蔔糕冷凍宅配 | 蘿蔔糕 | 縣市、區、完整地址、收件人 | 依實際簽約與後台開放方式 |
| 餐車／現場取貨 | 實際開放品項 | 指定場次／取貨點 | 由場次設定決定 |

每張訂單需保存配送方式、運費金額快照、收件／門市快照、物流狀態、物流追蹤資訊及建立時間。設定改價不得影響舊訂單。

## D. 付款

- 付款方式由後台控制啟用／停用。
- 貨到付款、匯款、線上金流需分別定義狀態轉移。
- 顧客端填寫後五碼／上傳憑證不等於已付款。
- 付款成功只可由管理員核對或可信金流 webhook／後端驗證更新。
- 需保留付款紀錄、核對人、核對時間、退款／取消紀錄。
- 上線前必須確認銀行帳戶資料、付款方式與金流供應商；不得猜填。

### 已讀取到的設定狀態（2026-11-08）
- `payment_settings.enabled=false`，銀行名稱、分行及戶名目前為空值。這表示不能把現有匯款設定當成可直接上線的付款資料。
- `pickup_settings` 曾讀到全家 30、7-ELEVEN 45，兩者 enabled；這屬於涼糕超商冷藏寄放資料，不能當成蘿蔔糕冷凍店到店合約費率。
- 蘿蔔糕訂購開關目前 false，商品陣列目前空。
- 蘿蔔糕前端及 RPC 的 99／129／250 為硬編碼，尚未核實最新物流合約。

## E. 老闆後台

以單一登入入口及權限分組：
1. 訂單中心：涼糕送到府、超商寄放、蘿蔔糕、現場取貨分開篩選及處理。
2. 商品中心：涼糕口味、蘿蔔糕、周邊商品。
3. 價格／庫存中心：商品價格、日期價格、庫存、盤點、保留量。
4. 物流中心：配送方式、費率、開放狀態、服務範圍、門市資料、物流狀態。
5. 付款中心：付款方式、核對、退款、付款紀錄。
6. 會員中心：會員資料、權益、優惠、停權與客服處理。
7. 餐車中心：日期、服務地區、時間、當日口味與價格。
8. 擺攤中心：日期、服務地區、時間、當日口味；依既有規則可不公開價格。
9. 員工與權限：依職務分配最小權限；敏感個資另行授權。
10. 報表中心：訂單、營收、付款、物流、庫存、場次日結。
11. 公告中心：首頁、跑馬燈、活動、公告、異動通知。
12. 系統中心：維護模式、操作紀錄、備份、錯誤紀錄。

## F. 員工系統（暫緩）

依使用者最新決定，員工相關功能先不開發、不設定、不部署，包含員工登入、員工帳號／角色管理、PDA、掃碼、現場臨時單、出貨核對、員工庫存操作、餐車／擺攤員工日結及會員 QR Code 員工驗證。

目前僅保留未來可擴充的 API／資料權限設計原則，不建立員工操作流程、不要求 PDA 型號，也不把員工功能列入本階段上線條件。未來若要啟動，另行排期與核准。

## G. 資料與安全底線

- Supabase Auth UID 作為會員識別；訂單聯絡資料不是會員主檔。
- RLS 必須依會員 UID 與管理員角色授權；員工／工作站授權待員工系統啟動時再規劃。
- 不把 service_role／secret key 放入 App、PDA 或瀏覽器。
- SECURITY DEFINER RPC 固定 search_path、限制 EXECUTE、驗證開單狀態、價格、庫存、配送、數量與權限。
- 不讓 anon 直接 INSERT 訂單主表或明細繞過 RPC；公開下單流程必須經受控函式。
- 付款狀態不可由用戶端自行更新。
- 敏感地址、電話、匯款資料、訂單憑證依最小權限存取。
- 操作與重要狀態變更留稽核紀錄。
- RLS disabled 的表（例如 `merch_backend_sync`）先確認有效 grants、API 暴露與外部後台用途，不可直接開 RLS 造成既有同步中斷。

## H. 已知需修正／確認的整合缺口

1. 涼糕送到府 RPC：需完成完整驗證，確認最低盒數、地區開放、庫存扣減、地址保存、會員關聯與明細讀取權限。
2. 涼糕超商冷藏寄放 RPC：費率目前由前端傳入；應改由可信設定讀取。明細快照應取資料庫驗證過的名稱與價格。需檢查地區啟用、門市白名單及重複品項。
3. 涼糕訂單讀取：`orders` 有會員本人讀取 policy；`order_items` 目前讀取 policy偏向管理員，會員 App 需有安全的本人明細查詢。
4. 蘿蔔糕 RPC：兩個 overload 均未在函式內驗證開單開關；新舊版運費硬編碼；舊 overload 仍可執行。
5. 蘿蔔糕顧客查詢：目前訂單／明細 SELECT policy 僅管理員，需設計安全的顧客本人查詢方式。
6. 付款：目前 `payment_settings` disabled 且銀行資訊空白；需確認實際收款資料與核對責任。
7. 物流：需確認涼糕冷藏寄放、蘿蔔糕冷凍店到店、冷凍宅配三種費率與合約；不得共用錯誤費率。
8. 會員：建立正式會員 profile、本人資料讀取／更新、訂單關聯流程；不自動認領歷史訪客訂單。
9. 庫存：統一庫存異動帳本與交易鎖定，避免 App、官網等顧客端同時下單造成超賣。
10. 通知：LINE／App 推播／電子郵件需確認供應商、token、同意與失敗重試；不得在前端放秘密金鑰。

## I. 一次部署的執行順序

### 1. 完整盤點（唯讀）
完成所有頁面、RPC、表格、RLS、Storage、Edge Functions、付款回呼、排程、LINE 整合與外部後台依賴盤點。

### 2. 完整規格凍結
產出 ERD、角色權限表、狀態機、物流設定規格、付款流程、API 契約、遷移相容策略及驗收案例。

### 3. 開發分支整合
先在 GitHub 開發分支完成 App／後台／API／migration 草案與自動化測試；不直接改正式官網或資料庫。

### 4. 測試環境演練
以測試資料驗證訪客、會員、管理員及所有配送付款組合；測試重複送單、庫存併發、退款、取消、通知失敗與舊版客戶端相容性。

### 5. 正式上線前備份與核准
先備份 DB／Storage／網站部署版本；逐項列出正式 migration、RLS、RPC、前端切換及回復方案。只有在使用者確認具體變更清單後，才可執行正式環境變更。

### 6. 一次切換與驗收
在維護窗口依序套用相容 migration、部署後端、部署網站與 App、驗證訂單全流程、確認回復點。官網保持可用，必要時以功能旗標分批開放而非直接停站。

## J. 尚不能代填的真實營運資料

為避免錯收款、錯收運費或無法出貨，下列資料需以實際合約／公司決策為準：
- 蘿蔔糕全家冷凍、7-ELEVEN 冷凍、冷凍宅配的最新簽約費率與服務範圍。
- 涼糕宅配是否有運費、COD 代收費及配送限制的最新合約規則。
- 匯款銀行、分行、帳號、戶名，以及是否啟用線上金流。
- 實際開放的配送區域、每日配送日期與截單時間。
- PDA 實機型號／掃碼方式與員工角色清單。
- App 商店發行者資料、隱私政策與推播供應商設定。

這些是唯一需要依實際營運資料核定的設定；其餘系統流程、欄位、權限、測試與部署工作可先完整規劃，不再拆成零散詢問。

## K. 本文件完成定義

「一次設定好」不是只把按鈕放進 App，而是以下項目全部通過：
- 顧客 App、官網、老闆後台資料一致；員工系統與 PDA 不在本階段。
- 所有訂單流程能建立、查詢、付款核對、出貨、取消及留存紀錄。
- 運費／商品價格／庫存均由可信資料來源計算。
- 訪客、會員、管理員權限測試通過；員工權限待未來階段。
- 正式資料遷移有備份、相容方案及回復方案。
- 舊官網正常運作，既有訂單與資料不遺失。
